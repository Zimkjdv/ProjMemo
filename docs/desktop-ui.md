# ProjMemo 桌面 UI 設計與驗收

更新日期：2026-10-16。這份文件保存目前操作規格、設計取捨與 R06 原始規劃；不是第二份待辦清單。最新未完成項目以 [ROADMAP.MD](../ROADMAP.MD) 為準，完成與驗收紀錄見 [CHANGELOG.MD](../CHANGELOG.MD)。

## 定位與保留的設計

個人部署、桌面優先、Python .venv、SQLite；不新增手機需求，不為 UI 改寫前端框架。卡片與明細共用同一份 DOM、表單及事件，避免複製表單、重複 ID 或切換時丟失草稿。

卡片採穩定 55:45 雙欄：左側 URL／備註，右側帳號／交接／環境；窄桌面自然退化單欄，不使用固定高度或瀑布流。五個分類使用原生錨點與 sticky 內容導覽，捲動追蹤不改寫歷史。導覽與區塊標題兩處數量依使用者評估保留，不再套用「固定導覽可用即隱藏區塊計數」。

內容區標題 1.075rem、主要文字 14–15px、次標籤 12.5px；不改首頁厚黑標題或設定頁字級。選中態與鍵盤焦點分開，更多操作始終可見。空狀態精簡但保留新增入口與安全說明。

## 長內容與編輯

- 長備註預設約三行純文字摘要，可展開完整 Markdown；表格、程式碼不硬裁切。
- 長網址與帳號的主機／登入名稱預設最多兩行，提供明確展開／收合；沒有 JavaScript 時呈現完整原文。
- 複製始終取原始 code 節點，不複製截斷摘要，不新增密碼複製或解密請求。
- 明細模式的五類編輯表單占用自己的完整列，不遮住鄰近列；卡片模式保留原有操作選單。
- 切卡片／明細不視為取消，保留新增與編輯草稿、手動展開及備註分頁；已顯示與延遲回傳的密碼仍套用既有遮蔽政策。
- 取消、點外／Escape 關閉編輯選單沿用共用確認：未修改直接關閉，有修改可保留或明確捨棄；密碼不回填或寫入 storage。R05 已交付後端欄位驗證、安全頁內錯誤與全頁離開提示，見 [表單說明](forms.md)。

## 首頁列表偏好

`projmemo.listPreferences.v1` 在目前瀏覽器 origin 的 localStorage 保存已套用的檢視、每頁筆數、狀態及搜尋詞；不保存頁碼、專案內容、表單草稿或保管庫資料。只讀首頁的列舉狀態，未知欄位不複製到儲存。

任何明確的 `view`／`page_size`／`page`／`q`／`status` URL 參數都優先，包含空篩選；不把舊偏好混入分享／書籤 URL。只有未指定列表參數的首頁會還原偏好，以 replace 導向完整 URL 並回到第 1 頁，不增加歷史迴圈。內容頁仍使用獨立的 `projmemo.detailView`。

搜尋詞最多記住 256 個字元，較長搜尋仍可使用但不保存到偏好；已保存的搜尋詞是一般瀏覽器資料，請勿把密碼或 Key 當搜尋詞。程式僅保存實際套用的篩選，不讀未送出的輸入。壞 JSON、非法枚舉、過大的偏好或 storage 被禁止時回退至原生 URL／表單。

「重設列表」回復卡片、10 筆、空篩選與第 1 頁，先清除舊偏好，回到列表後記住預設值；空結果的「清除篩選」只清除搜尋／狀態，保留檢視與筆數。兩個入口在沒有 JavaScript 時仍有可用的明確 URL。

## 大量備註的取捨與量測

本輪隔離假資料基線含 250 筆備註、30 筆帳號、3 個 URL、10 筆交接與 10 筆環境說明。加入備註分頁前，TestClient 三次完整 HTML 請求為 1277.3／796.4／766.3 ms、1,408,192 bytes；這包含路由與模板渲染，不是純 SQL、真實網路或 Windows 使用者端效能的基準。

以下是 R06 歷史取捨，現行實作已由 R05 的 [伺服器端分頁](note-paging.md) 取代：

因此超過 50 筆備註時啟用前端輕量分頁：預設 20 筆，可選 10／20／50／全部；按既有排序瀏覽，不移除資料或改變匯出。分頁只在目前頁面保留，不持久化備註內容；切檢視保留目前頁。開啟編輯選單時暫停換頁／改筆數，顯示原因，避免隱藏編輯草稿。只量測可見備註，隱藏備註不反覆展開量測。

這降低可見列數與長頁滾動負擔，**不降低完整 HTML／DOM 大小**。目前不加入區塊搜尋或排序；若實際使用達數百／數千筆，應由 R03／R10 評估真正伺服器端分頁、按需載入、索引與內容搜尋，並設計跨請求的草稿政策，不能把前端隱藏視為資料量問題全已解決。

#### 2026-10-14 專案內頁 UI 分析與後續分批計畫

依據使用者提供的 `ProjMemo_UI優化建議.md`、專案內容截圖，以及 `app/templates/project_detail.html`、`app/templates/access_accounts.html`、`app/static/styles.css`、`app/static/project-detail.js`、`app/static/vault.js` 與既有檢視測試核對。以下現況表保留 `6c05ec0` 的分析基線；已交付批次以 Changelog 為準。以下是對建議的取捨，不代表文件中所有方案都要實作。優先級為本輪 UI 的相對順序，不重新開啟已完成的全專案 P0。

**判斷：主要問題是內容分配與操作層級，不是缺少顯示模式。** 卡片／明細已存在，應沿用同一份內容與表單 DOM。設定頁的等高雙卡片適合短表單，專案內容則長短不一，不應用固定高度或強制等高製造空白。

| 建議／觀察 | 程式現況與原因 | 決策 |
| --- | --- | --- |
| 左長右短 | `.detail-main` 固定放 URL、備註、帳號，`.detail-side` 只有交接、環境；欄寬約 60:40 | 調整為較均衡且穩定的分類配置，長文另外收合；不以自動搬動卡片追求完全等高 |
